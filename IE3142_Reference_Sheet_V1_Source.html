1. DevSecOps Foundations & Shift-Left LEC 01

DevSecOps: Culture, automation, and platform design integrating security as a shared responsibility throughout every stage of the software delivery lifecycle (Plan to Monitor).

Traditional SDLC vs DevOps vs DevSecOps
ModelFocusSecurity Timing & Weakness
WaterfallSiloed, sequentialLate pre-release gate; 10–100× fix cost
DevOpsDev+Ops velocitySpeed prioritized; security bypassed
DevSecOpsDev+Sec+OpsShift-Left; continuous, automated security
Four Central DevSecOps Principles
  • Shared Responsibility: Security owned by all (Dev, QA, Ops, Sec), not just a siloed security team.
  • Security Automation: Automated checks (SAST, SCA, secrets, DAST) embedded in CI/CD pipelines.
  • Continuous Security: Security applied iteratively at every single release cycle and stage.
  • Continuous Monitoring: 24/7 observability of logs, telemetry, configs, and runtime behaviors.
Shift-Left Security Rationale
Reqs ($1×) → Design ($5×) → Code ($10×) → Test ($15×) → Prod ($100×)

Why Shift Left? Flaws caught early are orders of magnitude cheaper, reduce release delays, empower developers, and prevent systemic production incidents.

Security Integrated per SDLC Phase
  • Requirements: Abuse cases, security user stories, compliance, data classification.
  • Design: Architectural threat modeling, trust boundaries, secure patterns.
  • Coding: Secure coding standards, IDE linters, peer review, input validation.
  • Testing: Automated SAST, SCA, secrets detection, staging DAST.
  • Deployment: Hardened IaC, immutable images, automated security gates.
  • Operations: Continuous monitoring, SIEM, IDS/IPS, patch management, IR.
2. Secure Coding Practices LEC 02

Secure Coding: Proactive software development preventing CIA triad compromise and OWASP Top 10 vulnerabilities.

4 Core Secure Coding Habits
  • 1. Input Validation: Treat ALL external input as untrusted. Use Allow-list (regex, type, range, length) over block-lists. Canonicalize/normalize first → validate → use.
  • 2. Parameterized Queries: Primary defense against SQLi. Separates executable SQL command from untrusted data parameters.
  • 3. Output Encoding: Primary defense against XSS. Context-aware sanitization (HTML body, attributes, JS, URLs). E.g., `<` → `&lt;`.
  • 4. Least Privilege: Services & DB users run with bare minimum permissions; restricts attacker blast radius.
SQLi Vulnerable vs Secure Example
# INSECURE (Concatenation): "SELECT * FROM users WHERE name='" + user + "'"
# SECURE (Parameterized): cursor.execute("SELECT * FROM users WHERE name=?", (user,))
2. AuthN, AuthZ & Secure Logging LEC 02
Authentication vs Authorization
DimensionAuthentication (AuthN)Authorization (AuthZ)
QuestionWho are you?What can you access?
ControlPassword, MFA, SSO, TokenRBAC, ABAC, ACL, Scopes
DefenseArgon2id, bcrypt, rate-limitDefault deny; check every request (prevents IDOR)
  • Password Hashing: Use modern memory-hard functions: Argon2id, bcrypt, PBKDF2. Never use MD5, SHA-1, or plain SHA-256.
  • Logging Rules: Log AuthN failures, privilege escalation, admin actions. NEVER log: plaintext passwords, session tokens, API keys, full PAN, or PII.
  • OWASP Core Focus: Injection, Broken Auth, Sensitive Data, XXE, Broken Access Control, Security Misconfiguration, XSS, Insecure Deserialization.
3. 12 Secure Design Principles LEC 03

Secure Design vs Coding: Design governs system architecture and boundaries; coding governs implementation bugs.

PrincipleCore Exam Definition & Application
1. Defense in DepthLayered controls; if one fails, others prevent breach.
2. Fail SecurelyExceptions/errors default to safe, closed state (no bypass).
3. Least PrivilegeMinimum permissions needed for minimum required time.
4. Fail-Safe DefaultsDefault to DENY; explicitly grant permissions.
5. Secure DefaultsOut-of-box configs are secure (ports closed, TLS on).
6. Minimize SurfaceDisable unnecessary ports, protocols, services, and APIs.
7. Separation of DutiesCritical actions require 2+ distinct roles/approvals.
8. Complete MediationAuthorize every single access to every object; no cached checks.
9. Economy of MechanismKeep security design small, simple, and verifiable.
10. Open DesignSecurity relies on secret keys, never design secrecy (Kerckhoffs).
11. Least Common Mech.Minimize shared channels/resources across tenants.
12. Psych. AcceptabilitySecurity must be usable; users won't circumvent it.
3. Threat Modeling & STRIDE LEC 03

Threat Modeling: Structured technique to identify assets, threats, and mitigations before system construction.

1. Assets → 2. DFD / Boundaries → 3. STRIDE → 4. Mitigate

Trust Boundary: Border where data/control transitions between privilege levels (e.g., Internet → API → DB).

STRIDE Threat Classification Table
ThreatViolatesExam Definition & Mitigation
S – SpoofingAuthenticityImpersonating user/process. → MFA, TLS, AuthN
T – TamperingIntegrityUnauthorized modification. → Hashes, HMAC, TLS
R – RepudiationNon-repudiationDenying an action. → Tamper-proof audit logs
I – Info DisclosureConfidentialityData leakage/exposure. → AES-256, TLS 1.3, ACLs
D – Denial of SvcAvailabilityResource exhaustion. → Rate limit, DDoS shield
E – Elev. of Priv.AuthorizationGaining higher rights. → RBAC, least privilege
Risk Assessment & 4 Treatments

Formula: $\text{Risk} = \text{Likelihood} \times \text{Impact}$

  • Mitigate: Apply security control to lower risk (e.g., add WAF).
  • Avoid: Eliminate risky feature/operation entirely.
  • Transfer: Shift risk to 3rd party (Cyber insurance, SaaS SLA).
  • Accept: Acknowledge residual risk with executive approval.
3. Security Design Patterns LEC 03
  • Secure Gateway: Single entry point enforcing TLS, AuthN, rate limiting, and request inspection before routing internally.
  • Layered Defense Pattern: Perimeter Firewall → WAF → DMZ API Gateway → mTLS Microservices → Encrypted DB with isolated credentials.

Data Resilience & Network Controls
  • RTO: Max acceptable downtime duration before restore.
  • RPO: Max acceptable data loss time window (age of data).
  • IDS vs IPS: IDS = passive, out-of-band alerts; IPS = active, inline blocking of malicious traffic.
  • WAF: Layer 7 application inspection (SQLi, XSS filtering).
  • IAM Models: RBAC (roles), ABAC (attributes/context), DAC (owner controls), MAC (fixed security labels).
  • Hardening & IaC: Enforce CIS baselines, disable unused ports, prevent configuration drift via declarative Terraform/Ansible.
5. Containers & Kubernetes LEC 05
Virtual Machines (VM) vs Containers
Virtual Machines (VM)Containers (Docker)
Hypervisor + Full Guest OSShares Host OS Kernel (namespaces/cgroups)
Heavy overhead, minutes bootLightweight, millisecond startup
Strong hardware isolationProcess isolation; container escape risk
Docker & Container Hardening
  • Non-Root: Use `USER nonroot`; avoid UID 0. Drop caps: `--cap-drop=ALL`.
  • No Privileged: Never pass `--privileged`. Never mount `/var/run/docker.sock` inside containers (prevents escape).
  • Secrets: Never hardcode in Dockerfile (`ENV`/`ARG`); use runtime vaults.
  • Runtime: Read-only rootfs (`--read-only`), seccomp, AppArmor.
Kubernetes (K8s) Architecture & Security
  • Control Plane: API Server (mTLS/RBAC), etcd (encrypted at rest), Scheduler, Controller Mgr.
  • Worker Node: kubelet, kube-proxy, container runtime, Pods.
  • Security Controls: K8s RBAC (Roles/Bindings), `NetworkPolicy` (default deny pod ingress/egress), Pod Security Standards (PSS/PSA).

7. Monitoring & Incident Response LEC 07

Continuous Security Monitoring (CSM): Real-time observability of telemetry. Feedback loops back to SDLC Plan.

  • Log Management: Sync UTC clocks via NTP. Must log: timestamp, src IP, user, action, result. Mask secrets/PII; use tamper-evident storage.
  • SIEM: Aggregates, normalizes, correlates multi-source logs. False Positive = benign flagged bad; False Negative = breach missed.
Incident Response (IR) 6-Phase Lifecycle
1. Prep → 2. Detect → 3. Contain → 4. Eradicate → 5. Recover → 6. Lessons
  • Containment: Short-term (isolate VM, revoke tokens) & long-term.
  • Forensics: Preserve bit-stream copies (work on copies, not live), verify SHA-256 hashes, maintain strict Chain of Custody.

GRC: Governance (oversight/policy) + Risk (management) + Compliance (legal proof). Compliance ≠ Security (compliance is baseline; security is operational defense).

9. Secure Serverless & Cloud-Native LEC 09

Serverless / FaaS: Event-driven, auto-scaling, ephemeral execution (AWS Lambda, Azure Functions). Servers exist, but customer does not manage OS/servers!

Shared Responsibility in Serverless
  • CSP Manages: Physical infra, host OS, container runtime, auto-scaling, platform availability.
  • Customer Manages: Function code, IAM execution roles, API gateway auth, secrets, data encryption, third-party libraries.
Serverless Threats & Mitigations
  • Excessive Permissions: Function compromise spreads. → Enforce scoped per-function IAM least privilege.
  • Insecure APIs: Public invocation. → API Gateway auth (JWT/OAuth2), TLS, WAF.
  • Secrets Leak: Plaintext in env vars. → AWS Secrets Mgr / Key Vault.
  • Event Injection: Malicious queue/payload. → Validate all events.
  • Denial of Wallet (DoW): Flood of event triggers causes massive financial billing spikes. → API throttling, concurrency limits, budget kill-switches & billing alarms.
