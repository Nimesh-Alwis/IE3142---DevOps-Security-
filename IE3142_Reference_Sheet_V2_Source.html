1. DevSecOps & Shift-Left SDLC LEC 01 | Q1, Q3

DevSecOps: Integrating security across every phase of SDLC. Security is a shared responsibility of Dev, Sec, and Ops (not an isolated final gate).

Shift Left: Moving security activities to the earliest stages (Requirements & Design) instead of waiting for pre-release testing.

2. Five Core Secure Coding Practices LEC 02 | Q1, Q3(b)

1. Parameterized Queries (Prepared Statements): Defeats SQLi (OWASP A03). Database treats user input strictly as literal data, never executable SQL command.

// VULNERABLE: "SELECT * FROM users WHERE name = '" + name + "'" // SECURE: cursor.execute("SELECT * FROM users WHERE name = %s", (name,))

2. Allow-list Input Validation: Define allowed chars, length, type, regex (e.g. `/^[a-zA-Z0-9_]{3,20}$/`). Fails closed against unknown attacks. Reject invalid input (never "sanitize & use"). Canonicalize/decode before validation.

3. Context-Aware Output Encoding: Defeats XSS (A03). Converts special characters to safe entities (`<` → `&lt;`, `>` → `&gt;`, `"` → `&quot;`) at browser display time.

4. Memory-Hard Password Hashing: Never use MD5/SHA-1/SHA-256. Use Argon2id, bcrypt (work factor ≥ 12), or PBKDF2 with unique salt per user to defeat GPU brute-force.

5. Complete Mediation & Server-Side AuthZ: Verify authentication & role on every request. Never trust client-side flags.

if (user.role != "ADMIN") return response.status(403).send("Forbidden");

DB Least Privilege: App DB user gets only `SELECT, INSERT, UPDATE` (never `DROP`, `ALTER`, or `GRANT`).

AuthN vs AuthZ & Secure Logging
  • AuthN: Validating identity (MFA, password, WebAuthn).
  • AuthZ: Enforcing permissions (RBAC, ABAC, least privilege).
  • Log MUST include: UTC timestamp (NTP), user ID, IP, event, result.
  • Log NEVER contains: Passwords, API tokens, PAN (credit card), PII.

4. Threat Modeling, STRIDE & DREAD LEC 03 | Q1, Q2(i), Q3(c)

Threat Modeling: Structured process in Design Phase to identify, analyze, and mitigate threats before code is written.

4 Core Questions: 1. What are we building? 2. What can go wrong? 3. What will we do about it? 4. Did we do a good job?

Why in Design Phase? Shift Left: architectural flaws are caught before implementation; saves rework costs; establishes test cases & security requirements.

Assets: High-value targets (Student/Patient data, credentials, exam questions, marks/results, transactions, audit logs, API keys).

Trust Boundary: Where data passes between different privilege levels (e.g. Client Browser → API Gateway → DB Server).

STRIDE Threat Classification & Controls
ThreatViolatesExam Scenario Example & Control
S – SpoofingAuthenticationAttacker logs in with stolen user password. → MFA, strong password policy, account lockout
T – TamperingIntegrityStudent/attacker alters marks or transaction amounts. → Server-side validation, HMAC, digital signatures
R – RepudiationAccountabilityLecturer/user denies altering marks/sending money. → Tamper-proof audit logs + UTC time
I – Info DisclosureConfidentialitySQLi exposes student marks or patient records. → Parameterized queries, AES-256, TLS 1.3
D – Denial of SvcAvailabilityFlooding results portal with requests on release day. → Rate limiting, WAF, auto-scaling
E – Elev. of Priv.AuthorizationStudent calls `/admin/users` directly. → RBAC, server-side role check, least privilege
DREAD Risk Scoring & Risk Treatments

DREAD Formula: Risk Score = (Damage + Reproducibility + Exploitability + Affected Users + Discoverability) ÷ 5 (Scale 1–10). Score ≥ 7.0 = High Priority.

4 Treatments: Mitigate (controls), Avoid (drop feature), Transfer (cyber insurance/SaaS SLA), Accept (signed executive approval).

Three Core Infra Protections (Bank Scenario)
  • 1. Network Segmentation & Private Subnets: Place DB (RDS) in private subnet with no public IP. Security groups allow port 3306 only from API tier. WAF on public ALB/Gateway.
  • 2. IAM Least Privilege & MFA: Stop root account usage; enforce MFA for all users; issue short-lived STS/SSO role credentials instead of long-lived access keys.
  • 3. Data Protection: S3 Block Public Access; encrypt S3 and RDS at rest using AWS KMS (AES-256); TLS 1.3 in transit.
  • IaC Security (Shift-Left Infra): Write infra in Terraform/CloudFormation; scan in pipeline using Checkov/tfsec/KICS before provisioning.
Resilience & Access Models
  • RTO: Max acceptable downtime duration before restore.
  • RPO: Max acceptable data loss time window (age of data).
  • IDS vs IPS: IDS = passive detection/alert; IPS = active inline blocking. Signature = known attacks; Anomaly = baseline deviation (catches zero-days, more false positives).
  • IAM Models: RBAC (roles), ABAC (attributes: user, time, device), DAC (owner decides), MAC (strict labels/classifications).

6. Docker Architecture & Container Security LEC 05 | Q1, Q2(iii), Q4(b)

Docker: Open platform to build, ship, and run applications using OS-level virtualization. 2 Advantages: 1. Portability/consistency ("runs anywhere"); 2. Lightweight & rapid startup (shares host kernel).

Docker Architecture Components
Client (CLI) → Daemon (dockerd) → Image → Container ↔ Registry
  • Docker Client: Primary CLI interface (`docker build`, `run`, `pull`).
  • Docker Daemon (`dockerd`): Background engine managing images, containers, networks, and storage volumes.
  • Docker Image: Read-only, layered template with app code & deps.
  • Docker Container: Runnable, isolated instance of an image with a thin writeable top layer.
  • Docker Registry: Central repository storing & distributing images (Docker Hub, AWS ECR, Harbor).
Image vs Container & VM Comparison
Docker ImageDocker Container
Static, read-only blueprintDynamic, running instance
Immutable set of layersContains state + writeable layer

VM vs Container: Containers share host OS kernel via cgroups/namespaces (fast, lightweight, but risk of container escape). VMs have full guest OS via hypervisor (heavy, stronger hardware isolation).

4 Container Security Risks & Controls
  • 1. Running as Root: Compromise gives root on host. → Add `USER nonroot` (UID 10001); drop caps (`--cap-drop=ALL`).
  • 2. Privileged Container / Socket: `--privileged` or mounting `/var/run/docker.sock` allows escape. → Disable privileged mode; never mount docker.sock.
  • 3. Secrets in Image: Hardcoded `ENV`/`ARG` secrets stored in layers. → Inject at runtime via Vault/K8s Secrets; use `.dockerignore`.
  • 4. Bloated / Vulnerable Images: Unpinned tags (`:latest`) contain CVEs. → Use pinned minimal base (`python:3.12-slim`), scan with Trivy/Grype.
Secure vs Insecure Dockerfile
# INSECURE DOCKERFILE: FROM python:latest ENV DB_PASS=Secret123 \ API_KEY=key-9876 RUN apt-get update && apt-get install -y gcc vim openssh-server USER root EXPOSE 22 5000
# SECURE DOCKERFILE: FROM python:3.12-slim RUN useradd --create-home --uid 10001 appuser WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt COPY --chown=appuser:appuser src/ ./src/ USER appuser EXPOSE 5000
7. Kubernetes (K8s) Architecture & RBAC LEC 05 | Q1, Q4(c)

K8s Architecture: Control Plane (API Server [mTLS/auth], etcd [encrypted secrets], Scheduler, Controller Mgr). Worker Nodes (kubelet, kube-proxy, container runtime, Pods).

9. Continuous Monitoring & SIEM LEC 07 | Q1, Q4(e)

Continuous Security Monitoring (CSM): Real-time observability of infrastructure, container, and cloud telemetry. Feedback loops back to SDLC Plan.

  • Why Important: Early threat detection, rapid containment, visibility into cloud actions, compliance & audit readiness.
  • Log Management: Sync clocks via NTP (UTC). Mandatory fields: timestamp, src IP, user ID, action, result. Tamper-proof WORM storage. Redact PII.
  • SIEM (Security Information & Event Management): Centralizes, normalizes, and correlates logs from multiple sources (CloudTrail, K8s audit, firewalls). Tools: Microsoft Sentinel, Splunk, Elastic.
  • Key Triggers: Unusual outbound data transfer (exfiltration alerts), multiple failed logins, privileged pod creation, bulk secret reads.
  • Alert Accuracy: False Positive = benign flagged bad; False Negative = breach missed (dangerous!).
10. Incident Response (IR) 6-Phase Lifecycle LEC 07 | Q1, Q4(f)
1. Prep → 2. Detect → 3. Contain → 4. Eradicate → 5. Recover → 6. Lessons
  • 1. Preparation: Establish IR plan, team roles, communication channels, tested backups, and access to forensic tools.
  • 2. Detection & Analysis: Validate alerts, scope affected systems/data, determine attack vector, analyze indicators of compromise (IOCs).
  • 3. Containment: Short-term: Isolate compromised pods/nodes, revoke stolen tokens, block attacker IP. Long-term: Segment network to prevent lateral spread.
  • 4. Eradication: Remove malware/malicious packages, patch exploited vulnerabilities, re-image nodes, rotate DB passwords & all secrets.
  • 5. Recovery: Restore clean systems from verified backups, test in staging, gradually return to production, heighten monitoring.
  • 6. Lessons Learned: Post-incident review, root-cause analysis (RCA), update pipeline security gates, report breach to regulator within 72 hours (GDPR Art 33).
  • Digital Forensics & Chain of Custody: Work on bit-stream copies (never live disk); verify SHA-256 hashes; log every transfer and custodian to maintain legal evidence integrity.
11. Governance, Risk, Compliance & Healthcare LEC 08 | Q1, Q4(d)

GRC: Governance (oversight/policies) + Risk (management) + Compliance (legal proof). Compliance ≠ Security (compliance is minimum baseline).

3 Healthcare Controls to Protect Patient Data
  • 1. Technical: Encrypt at rest (AES-256) & transit (TLS 1.3); MFA; RBAC.
  • 2. Administrative: Access review policies, staff security training, IR plan.
  • 3. Physical: Data center access badges, encrypted workstation disks.
  • Control Classes: Preventive (MFA, WAF), Detective (SIEM, IDS), Corrective (backups, patch), Compensating (isolated VLAN if no MFA).
12. Secure Serverless Architectures & DoW LEC 10 | Q1

Serverless / FaaS (Lambda): Event-driven, auto-scaling, ephemeral execution. CSP manages hardware, OS, runtime; Customer manages code & IAM!

  • Denial of Wallet (DoW): Malicious flood of event triggers exhausts cloud budget instead of crashing system. → API rate limiting/throttling, concurrency limits, budget kill-switches & billing alarms.
  • Serverless IAM: Scoped per-function least privilege (limits blast radius; never share single AdministratorAccess role).
